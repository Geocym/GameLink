# GameLink v0.2.9 — reliability validation

Use a disposable copy of the data directory and a test Streamer.bot action. Exit GameLink before copying data. Do not intentionally terminate a production stream or corrupt the only copy of your data.

## Build

Open GameLink.sln in Visual Studio and restore/build. Target remains net10.0-windows. No new packages. The source archive has not been compiled in the packaging environment.

## Normal operation

- Verify existing settings, history, Steam progress and routing survive upgrade.
- Unlock an achievement; check metadata, session counts, history and delivery. The `achievement-scan.pending.json` file should disappear after forwarding, and `receipts/<eventId>.json` should exist.
- Test offline recovery in individual and summary modes, including completion. Confirm no new parent event on replay.
- Test rejected event with corrected route, including a second destination that already accepted it. Clear history and replay with skip accepted enabled; for an event accepted under v0.2.9 the receipt should still exclude that destination.
- Test intentionally replaying to an accepted destination with skip disabled.

## Interrupted operations (debugger recommended)

- Break after journal write and before snapshot write in SteamAchievementMonitor.Scan. Terminate process, restart with monitoring enabled. Confirm journal recovery, delivery, and snapshot progress.
- Break after queue save and before journal deletion. Restart; check that the same event ID is not enqueued again. Repeat for an offline summary.
- Break after Replay saves the replacement queue entry but before RejectedForm deletes old records. Restart and connect. Verify old selected records are removed before delivery, and history uses the same event ID.
- Break after moving the destination to backup in DataMigration.ApplyAtStartup. Restart; verify original mode and destination restored, then schedule again. Repeat after flag activation; verify target remains active. Keep all backups until verified.
- Test a rejected or disconnected delivery and normal reconnect. A remote acknowledgement lost before local persistence can still cause duplicate delivery.

## Diagnostics and storage

- Diagnostics > Support bundle: open ZIP and inspect diagnostics.json. It contains allowlisted system and status fields only, no raw logs, settings, payloads, usernames or passwords.
- In a disposable debug build, throw an unhandled exception on the UI thread; check `crashes` for a local report. Crash reports can contain private paths and exception details; review before sharing. No automatic upload.
- Open Manage storage, refresh, clear artwork/logs and compact history. Check UI responsiveness and that queue/snapshots/receipts are retained. SQLite contention can still delay other database operations.

## Known limits

The journal is recovered when Steam monitoring runs, not when monitoring is disabled. Optional enrichment and routing on recovery use current settings; summary mode and original IDs are preserved. A failure before the first journal write succeeds cannot be recovered from that journal. A crash before detection or during an acknowledgement remains outside exactly-once guarantees. Receipts are retained indefinitely for now and older acknowledgements depend on retained history. Action name/GUID aliases are not canonicalised. Migration recovery covers the destination replacement phase; interruption during initial staging may leave an orphan staging directory. Support bundle is intentionally minimal; raw logs and settings are excluded rather than relying on incomplete redaction. No automatic crash uploads.
